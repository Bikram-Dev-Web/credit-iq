# Load-test results

Measured with [k6](https://k6.io) v2.3.0 on 2026-10-24 (`loadtest/score.js`, raw summaries in `loadtest/results/`,
table generated by `python loadtest/report.py`).

| Endpoint | Load | Workers | RPS | p50 (ms) | p95 (ms) | p99 (ms) | Errors | Requests |
|---|---|---|---|---|---|---|---|---|
| /v1/score | open model, 20 req/s for 60 s | 1 | 20.1 | 27.0 | **46.2** | 176.0 | 0.00% | 1,222 |
| /v1/decide | open model, 20 req/s for 60 s | 1 | 20.1 | 25.2 | 54.9 | 265.6 | 0.00% | 1,222 |
| /v1/score | closed model, 8 VUs back-to-back for 60 s | 1 | 27.7 | 279.2 | 391.7 | 532.5 | 0.00% | 1,683 |
| /v1/score | closed model, 8 VUs back-to-back for 60 s | 3 | 23.6 | 312.8 | 509.8 | 663.4 | 0.00% | 1,446 |

**Target: p95 < 50 ms for single-applicant scoring on a laptop — met (46.2 ms at 20 req/s).** k6 enforced it as a
threshold for the latency run.

## Setup

- **Machine:** Intel Core i3-1215U (6 cores / 8 threads), 7.7 GB RAM, Windows 11. During the runs the machine had
  about 0.2 GB of free memory and other applications running (an IDE, a browser, other local servers), so these
  are numbers from a busy laptop, not a quiet benchmark host.
- **API:** `creditiq-api` (uvicorn, no reverse proxy), model v1 = logistic regression trained on the bundled
  **synthetic** data, policy `2026.10.1`, audit log in **SQLite** (the local default), every request written to the
  audit log synchronously. `RATE_LIMIT_SCORE` was raised for the runs; the default (600/min per key) would answer
  429 to the throughput run by design.
- **Requests:** 200 synthetic applicants (`loadtest/applicants.json`) chosen at random; 20 warm-up requests first.
  Latency includes validation, scoring, the exact explanation (top 8 reasons), policy evaluation, the audit write
  and JSON serialisation.

## Reading the numbers

- **Each request is CPU work** (the scikit-learn pipeline on one row, the explanation, then the policy). At about
  25–35 ms of compute per request, one Python worker serves roughly 28 req/s. Past that, requests queue, which is
  why the closed-model runs show 280–390 ms medians: that is queueing time, not scoring time.
- **More workers did not help on this machine:** three workers on a laptop with almost no free RAM and other
  busy processes competed for CPU and memory, and the SQLite audit store accepts one writer at a time. On a
  dedicated host with Postgres, add workers or replicas (the API is stateless apart from the model cache), or put
  batch traffic on `/v1/score/batch`, which scores rows vectorised.
- **Tail latency (p99)** comes from garbage collection and contention with other processes on the shared laptop.
- **What made the p95 target:** before the single-row fast path (`creditiq_core.explainability.explain_one`) the
  pipeline ran three times per request and p95 was 84 ms; running it once and aggregating contributions with a
  cached matrix brought scoring compute from 44 ms to 16 ms (outputs identical, tested).

## Reproduce

```bash
# API (any way you run it), then:
k6 run -e BASE_URL=http://localhost:8000 -e API_KEY=<analyst key> -e SCENARIO=latency \
       --summary-export loadtest/results/latency.json loadtest/score.js
k6 run ... -e SCENARIO=decide     --summary-export loadtest/results/decide.json loadtest/score.js
k6 run ... -e SCENARIO=throughput --summary-export loadtest/results/throughput.json loadtest/score.js
python loadtest/report.py
# or with Docker: docker run --rm -i --network host -v "$PWD/loadtest:/lt" grafana/k6 run /lt/score.js
```
